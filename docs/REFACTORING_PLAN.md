# Refactoring Plan — MudgalGastromedics OS

Derived from [`ARCHITECTURE_AUDIT.md`](./ARCHITECTURE_AUDIT.md). Findings are tagged
**F-n**, matching that document. Started as a proposal; items are now being applied
one at a time, module-by-module — each row is marked **✅ Done (date)** with the
actual implementation and verification evidence once complete, so this document has
become a work log for finished items and a proposal for the rest. Effort legend
matches `build-roadmap.md`: **S**≈hours · **M**≈1–3 days · **L**≈1–2 weeks ·
**XL**≈multi-week.

**Working rule for all four phases, restated from `CLAUDE.md`:** improve/refactor/
reuse/extend, never rewrite; one item per change-set, never sweep the whole app; every
change stays backward-compatible; never touch auth/RBAC/audit contracts as a side
effect of an unrelated fix. Each item below is scoped to be its own PR.

**Two hard-won lessons from this session's live-verification work, worth repeating for
any future one:**
1. **`.env.local` sets a real, live `DATABASE_URL`** (remote Neon Postgres) — every
   `next dev`/`next start` run reads and writes that database unless overridden. For
   any live check that isn't specifically testing the database integration itself,
   run with `DATABASE_URL=` (empty) prefixed to force the local JSON-file store
   instead — e.g. `DATABASE_URL= npx next dev -p <port>`. `rm -rf .data` before a run
   only gives a clean slate if `DATABASE_URL` is also unset for that run.
2. **`next start` forces `NODE_ENV=production`**, and `lib/staff-auth.ts`'s dev-only
   fallback admin password (`mgm-admin`) only applies when `NODE_ENV !== "production"`.
   A login POST that returns `200` with no error text is not proof of success —
   check the actual JSON body (`{"ok":true,...}`) or a positive content marker unique
   to the authenticated view, since most OS pages return `200` for unauthenticated
   visitors too (they render `WorkspaceLauncher` instead of erroring). Prefer
   `next dev` for any live check that needs a real staff session.

Also: shell variables set in one Bash tool call do not persist into the next one —
a login + follow-up-request sequence that relies on a cookie jar variable must run in
a single command block, or the follow-up requests silently send no cookies at all.
